## 1. 工作者規則

1. 全專案只使用本檔，不建立第二份藍圖、roadmap、分期表或流程規劃文件。
2. Codex 親自負責法典實作、藍圖編寫、全自動模式腳本及其他程式的唯讀實作差異比對，不得將實作比對交給其他工作者。Codex 不直接實作其他程式；比對後保留較佳且符合現行法典的實作，並更新法典、藍圖或全自動模式規則，不得為符合舊規劃而回退較佳實作。
3. 工作者以架構與功能施工為主；只有本藍圖明列的 parity、release 觀察窗、資源量測與收斂證據屬施工必要工作，不得擴張成全面測試或重複驗收。
4. 發現工作包與強制契約直接衝突時停止並回報，不自行改法或擴張 authority。
5. 實作優於舊規劃時保留已驗證實作，更新本檔的目標與殘項，不回退較佳實作。
6. 不建立 compat、shim 或臨時平行實作；遷移採 `shadow → parity → primary → retire`，完成後移除舊 owner。
7. 每次工作者提交或本檔修改後，指定法典工作者自動比對 current 程式、設定、registry 與 revision：
   - 施工完成：刪除工作項。
   - 部分完成：只保留可執行殘項。
   - 完成標示與實作不一致：撤銷完成標示。
8. 工作區可能有其他工作者變更；只修改自身檔案，不覆蓋、不重置、不順帶提交他人內容。
9. 未完成清單為空時仍須保留本藍圖；不得因暫無待辦事項刪除、改名或建立替代文件。
10. 未完成清單固定由 `P0` 開始連續編號；高優先度排在前方，同優先度維持依賴順序。新增、刪除或調整優先度後自動排序並重新編號，不保留舊編號或缺口。

## 2. 目標

主要目標：讓 C11 運行核心成為真正的常駐主體，逐步釋放 Python 的機械性工作，同時完整保留治理與安全語意。五核心語言責任及現行法典是唯一架構依據，取消舊版 Python／C# 混合雙宿主假設；架構目標不得誤報為已完成遷移。

### 2.1 五核心與語言責任

| 核心 | 正式責任分配 | 現階段應優先完成 |
| --- | --- | --- |
| 裁決核心 | C 決定性執行、C# 流程、Python 治理語意及必要最終裁決 | C shadow 與 Python 正典結果同位 |
| 權限核心 | C 權限熱路徑、C++ Audit Engine、C# 編排、Python 目錄 | 原生規則索引、授權與稽核閉環 |
| 運行核心 | C11 常駐主體 | 8 個 shadow 元件逐項取得 primary 資格 |
| 自動化核心 | C# 主體＋C primitive | Python automation 工作逐項外移 |
| 星澄助理 | TypeScript UI＋C# 後端 | 全域合規稽查與許可介面契約一致 |

- Python 保留已核定的治理語意與必要最終裁決；C 負責決定性規則與權限熱路徑，C++ 負責原生審計，C# 負責已授權流程編排。
- C 不得建立或修改治理規則；C# 不得繞過裁決、權限或擴張授權；原生規則索引只可投影 canonical permission directory。
- 禁止新增第二套 scheduler、orchestrator、IPC client、治理 authority 或權限來源。

- 星澄是獨立原生模型，不是核心、主宰或獨立工具。
- 星澄人格、自動修復、自我學習、自動編程與內部自我升級屬星澄能力。
- 星澄助理與星澄使用獨立身分組與獨立資料庫，不得混用或互相產生權限。
- 自動修復由星澄提出方案並執行受管流程；無法確定可修復時不得硬修、覆蓋或重置。
- 系統自動更新與自動修復開關留在星澄助理，支援單項許可；星澄自我學習與內部升級不設使用者開關，但仍受治理與資源閘約束。

### 2.2 Runtime 與模組

timer、polling、watcher、queue、scheduler、process lifecycle、health probe、檔案掃描、Git 協調、SQL maintenance、transport pump、test orchestration、已核准 audit check、cleanup、retention、reconciliation 與格式轉換，正式路徑由 C／C++／C# 或資料庫原生能力承載。

Python 只保留治理語意、最終裁決、法典工具、模型訓練及尚未完成 parity 的按需 adapter；完成即釋放。任何過渡 adapter 必須有 owner、替代目標、量測與退役條件。不得為移除 Python 而轉移 authority、破壞 fail-closed 或重寫尚未證明等價的治理語意。

- 持續減少 Python 套件、常駐程序、背景迴圈、中介層與重複實作；機械性能力優先收斂至既有 C11、C++、C# 或資料庫原生能力，不以另一套包裝層取代。
- 每個核心、模組、工具及 worker plane 必須登錄 CPU、記憶體、程序、執行緒、queue、deadline 與並行數硬上限；禁止 `unlimited`、空值或僅告警不限制。
- `CORE_BUDGET_CAP=5` 是核心工作量聚合上限，不得被子程序、工作者或語言 runtime 分拆繞過；資源計算涵蓋 GPTBridge 完整程序樹，不得只計單一 Python 程序。
- 達到上限時依 capability 執行拒絕、排隊、降級、釋放或停止，不得超額執行、隱藏資源占用或以提高上限掩蓋問題。

- 模組是唯一實際工作單位；核心不直接執行領域工作。
- 每模組單一能力、單一職責、按需啟動、版本化契約、有界資源、執行租約、receipt 與可回復生命週期。
- 執行模組以 C／C++／C# 為主；UI 使用 TypeScript；SQL 只做集合式資料運算。
- 模組規則由模組維護，權限核心集中索引；不是獨立權威，也不得進 Runtime 法典規則索引。
- 退役模組標記為垃圾，經星澄助理分類後由自動清理排程處理。

### 2.4 資料與檢索權威

- PostgreSQL：中央 canonical structured data、shared transport、central audit 的唯一 SQL authority。
- SQLite：owner-private operational state，`canonical=false`、禁止跨模組 authority、shared audit 或 permission authority；只允許有界降級並強制 reconciliation。
- Qdrant：語意索引，不取得 canonical authority；每次正式結果須回 PostgreSQL 驗證 scope、revision 與 locator。
- Git：程式碼與交付歷史；不取代 SQL 資料權威。
- 備份、快取、向量與模型輸出都不因存在而取得 authority。

```text
Caller
→ Information Channel
→ Permission / Scope
→ RagApplicationService
→ DAG Planner / Executor
→ CAG Gate
→ RAG Retrieval
→ Evidence Fusion
→ Reranker
→ Context Builder
→ Local LLM
→ Citation Validation
→ Result
```

- DAG 是 orchestration plane，不取代 Application Service。
- CAG 是有版本、有範圍的 acceleration/context reuse plane，不取代 RAG。
- RAG 是 canonical retrieval plane，保留 Hybrid／Code／Memory／Agentic 四子架構。
- PostgreSQL／Qdrant canonical 邊界不變；SQLite 仍只可 bounded degraded fallback。

### 2.5 依賴原則

優先標準函式庫、既有自研核心與作業系統 API。新增第三方套件必須證明標準能力不足、沒有既有 owner、資源與供應鏈成本可接受且有替代／移除路徑。密碼、資料庫協定、模型格式與作業系統安全能力不得為追求零依賴而自行重造。禁止第二套 scheduler、orchestrator、audit policy、governance authority 或 IPC client。

### 2.6 Git 收斂

1. worker 只提交自身明確路徑，永不 push；coordinator 是唯一整合與推送者。
2. 每個 worktree／HEAD generation 只建立一次共享 snapshot；status、diff、changed paths、merge-base、ahead／behind 與 affected scope 供所有 gate 共用。
3. dirty、HEAD、queue 與檔案事件驅動增量處理；週期掃描只作低頻保險。
4. 同一任務的穩定變更合併為一個語意提交；禁止每個小編輯或報告刷新各自提交。
5. 依 commit、受影響路徑與契約版本只處理受影響範圍。
6. generated runtime state、cache、暫存與非 canonical 重跑報告不得進 Git。
7. coordinator 批次整合後只推送一次；無新 commit 或同 generation 已同步時不得重做 fetch／merge／push。
8. 不得削弱 path scope、衝突停止、non-fast-forward／force-push 禁止或來源 revision 約束。

### 2.7 SQL 效能與治理

1. 依 interactive／transport／audit／reconciliation／maintenance／migration 分開量測 query count、round trips、p50／p95／p99、pool wait、lock wait、transaction age、rows scanned／returned、buffer hit、temp spill、WAL、CPU 與 I/O。
2. 優先移除 N+1、重複 lookup、`SELECT *`、無界 result、深 offset 與應用層逐列運算；改用明確欄位、set-based SQL、keyset pagination、prepared statement、bounded batch 及合規的 `COPY`。
3. 索引必須有真實 workload 與 plan 證據；檢查 join order、估算偏差、spill、sequential scan、unused／duplicate index。禁止無量測加索引。
4. 維持 workload lane 隔離；減少短連線、縮短 transaction、禁止 idle-in-transaction、統一 lock order，把網路／模型／檔案工作移出 SQL transaction。
5. 寫入採批次、idempotency key、避免無變更 update；不得停用 RLS、audit、ordering、generation fence 或 write provenance。
6. RAG scope／revision／metadata filter 儘早下推 PostgreSQL，chunk／locator 批次回查，避免每個 Qdrant point 一次 SQL。
7. SQLite 只優化 owner-private fallback；禁止以 SQLite 分流中央 authority 來製造表面加速。
8. partition、materialized view、denormalization、壓縮或 schema 變更必須走 migration、drift gate、RLS parity、回復與重建驗證。
