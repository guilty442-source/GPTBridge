## 1. 一句話結論

四層之中，只有 **Inference System 的外圍治理**（上下文窗格、取樣參數、資源調度、治理標記）是真實在跑的；
**Base Model 的本體**目前是 Ollama 第三方權重（`gemma4:e2b-it-qat`）＋一個統計式 n-gram 後備模型；
自有 PyTorch Transformer（`native_transformer/`）與其訓練迴路**已存在但完全未接線、未訓練、無法存讀**。
Pretraining 與 Post-training 目前都**不會更新任何神經權重**。

## 3. 逐層盤點

### 3.1 Base Model

**已經有的**

1. 生產路徑 A（星澄自有）：`StarAutoregressiveLanguageModel`，型別 `weighted-backoff-token-ngram`
   （`generative_language_model.py:112`），以權重化 token n-gram 計數抽樣生成，
   tokenizer 是正規表示式切詞（`generative_language_model.py:155`）。
   當事實保留檢查失敗時，輸出會直接回退成 grounding 原文（`generative_language_model.py:368-370`）。
2. 生產路徑 B（預設）：`StarTransformerRuntime` → loopback `POST /api/chat`（`transformer_runtime_http.py:83-128`），
   模型為 Ollama 的 `gemma4:e2b-it-qat`；推論結果會被標記 `third_party_weights_used: True`、
   `star_native_model_used: False`（`infer_transformer.py:59,87`）。
3. `native_transformer/`：真正的 PyTorch decoder-only 實作（RoPE、GQA、SwiGLU、RMSNorm、SDPA／FlashAttention、
   KV cache 類別、sampler、AdamW trainer、INT8/INT4 quantizer、Triton kernel 骨架）。
   但全 repo 只有 **1 處引用**，而且是註解（`xingcheng_tools/__init__.py:3`）。

**缺口**

- 無任何已訓練權重；全 repo 無 `torch.save`／`torch.load`，也無 `.safetensors`／`.pt`／`.gguf` 產物。
- 無 checkpoint 存讀／續訓 API；`XingChengConfig` 預設 `vocab_size=32000` 與 tokenizer 預設 8192 未對齊。
- tokenizer 為位元組級（`tokenizer.py:47-48`），BPE 合併規則未實作（`tokenizer.py:80`）。
- 執行環境是 `torch 2.13.0+cpu`，無 CUDA。

### 3.2 Pretraining

**已經有的**

- 訓練程式碼：`training/trainer.py:68-91`（forward → `loss.backward()` → clip → `optimizer.step()`）、
  `training/optimizer.py`（AdamW／SGD）、`training/data.py`（`TextDataset`＋collate）。
- 唯一呼叫者是自己的測試（3 步、4 句字串），且不存任何產物。
- 語料：`FIRST_PARTY_CORPUS` 約 45 句（16 意圖）＋ SQLite 19 筆。

**缺口**

- 無語料收集／清洗／授權標記管線；無 tokenizer 訓練；無預訓練 run、無 checkpoint、無續訓。
- 無 perplexity／loss 評估管線（現有 `capability_evaluation.py` 是 13 項布林規則檢查，不是語言模型評估）。
- 治理面：`training_repo_schema.py` 有 `transformer_training_dataset`／`_job` 表與狀態機，
  但**沒有任何執行器**呼叫（`transformer_training_repository_jobs.py` 只寫列與審計）。

### 3.3 Post-training

**已經有的（但不動權重）**

- 每次推論產生訓練候選（`native_inference.py:177-209`），經規則閘門
  （`gpt_training_gate.py`：意圖白名單、注入／憑證樣式、grounding 覆蓋率、事實保留）後
  （`local_ai_training.py:86-136`）寫入 `language_training_example` 並更新 n-gram 計數。
- Ollama 教師集成只負責**產生資料**（`local_ai_training.py:138-305`）。
- 基礎模型輸出被明確排除在自我訓練之外（`infer_transformer.py:95`）。
- 「權重重建」實際是重建 n-gram 計數（`local_ai_maintenance.py:46-57`），不是神經權重。

**缺口**

- 無 SFT／DPO／ORPO／RLHF／reward model；無 chosen-rejected 偏好資料（「preference」只出現在模型路由表）。
- 無工具呼叫訓練（tool calling 僅是模型角色標籤）。
- 無「SQLite 範例 → 訓練集」序列化器；`star-transformer-sft/v1` 只是字串常數。
- adapter 的 candidate／evaluation／release 表存在但**無寫入 API**，DB 全為 0 筆。

### 3.4 Inference System

**已經有的**

- 服務端上下文管理：窗格階梯 2,048–153,600、成功 3 次自動升窗、記憶體壓力自動降窗、
  每模型上限持久化（`transformer_runtime_context.py`、`transformer_runtime_catalog.py:19-23`）。
- 取樣：`temperature`／`top_k`／`top_p`／`repeat_penalty` 由 `transformer_runtime_request.py:199-236` 組裝；
  全域 KV cache 設定為 `OLLAMA_KV_CACHE_TYPE=q8_0`＋flash attention（`config/ollama-model-parameters.json:4-8`）。
- 資源治理：VRAM 判斷、模型預載／卸載、resident 策略、並發 semaphore。

**缺口**

- KV cache／prefix cache／上下文壓縮全部由 Ollama 內部處理，應用層沒有自己的快取與壓縮策略。
- 原生路徑的 `KVCache` 類別從未被實例化，解碼改用無上限 `torch.cat`（`modules/attention.py:84-85`）。
- 無 speculative decoding、無 continuous batching、無量化推論接線（quantizer 只被自己的測試呼叫）。
- 原生 sampler 已支援 top-p／repetition penalty，但無法從服務層呼叫。

## 4. 已確認的正確性缺陷（建置前必須先修）

> 這些是**唯讀檢視程式碼即可確認**的問題，全部位於未接線的 `native_transformer/`；
> 因為尚未上線，目前不影響生產行為，但會讓「先接線再修」變成錯誤順序。

| 編號 | 缺陷 | 位置 | 影響 |
| --- | --- | --- | --- |
| D1 | 只要傳入 `attention_mask`，`is_causal` 就變 `False`；而 generate 一律合成全 1 mask、trainer 也傳 mask 進模型 → **prefill 與 SFT 都是雙向注意力** | `modules/attention.py:97`、`inference/generate.py:51-52`、`training/trainer.py:78` | 訓練可輕易把 loss 壓到極低卻學不到自回歸能力；生成品質不可信 |
| D2 | 解碼步沒有傳 `position_ids`，`position` 變數算完沒用；RoPE 永遠從位置 0 取表 | `inference/generate.py:65,80`、`kernels/rope.py:76-80` | 快取解碼的位置語意錯誤 |
| D3 | `KVCache` 容器（`inference/kv_cache.py`）未被使用，改用 tensor 串接 | `modules/attention.py:84-85` | 長序列記憶體無上限 |
| D4 | 無 checkpoint 存讀；`Trainer.fit` 不落地任何產物 | `training/trainer.py` | 訓練無法續跑、無法交付 |
| D5 | tokenizer 與 config 詞表預設不一致（8192 vs 32000） | `tokenizer.py:26`、`config.py:18` | 接線時維度對不上 |

驗收建議（每項都要有測試）：
D1「改動序列尾端 token，前段 logits 不變」；D2「KV-cache 解碼 vs 全序列重算，逐 token logits 一致（1e-4）」；
D4「存讀往返 logits 完全相同」；D5「encode 出的 id 全數 < vocab_size 且 round-trip 還原」。

### 4b. Phase 0 執行結果（2026-09-19）

D1–D5 已修復並以測試鎖定；另發現並修復一個清單外的缺陷 F1。

| 編號 | 狀態 | 修復內容 |
| --- | --- | --- |
| D1 | 已修 | `_build_sdpa_mask` 產生 (B,1,S_q,S_k) 因果＋padding 合成遮罩；attention 僅在 q/k 等長且無 mask 時使用內建 causal；手動 fallback 亦支援位移因果 |
| D2 | 已修 | 解碼逐步傳入 `position_ids`（prefill `arange`、decode `prefix_len + step`） |
| D3 | 已修 | `Generator` 改用 `KVCache` 容器（預配置上限、`slice`/`update`），`attention` 快取回傳改為「本步新增切片」 |
| D4 | 已修 | 新增 `checkpoint.py`（`star-transformer-checkpoint/v1`：config/權重/tokenizer/雜湊、原子寫入、`.sha256` 側檔）；`Trainer` 支援 `checkpoint_dir`／`checkpoint_every` |
| D5 | 已修 | `XingChengTokenizer.from_config()` 對齊模型詞表 |
| F1 | 已修 | **`_repeat_kv` GQA 展開維度順序錯誤**（把新維度插在位置軸前），導致不同 head 的序列位置被交錯、注意力可看見未來 token；已改為 `(B, kv_heads, n_rep, S, D)` 展開 |

驗證：`tests/test_model.py` 20 項全數通過（原生套件就地執行，指令見附錄 A），
涵蓋因果性（有／無 mask、padding）、KV-cache 對全序列等價、greedy cache／no-cache 等價、
tokenizer 對齊、checkpoint 往返與竄改偵測、Trainer 落檔、60 步 overfit smoke（5.59 → < 4.59）。
治理稽核 `python -m governance_rule.execution.audit`：PASS。

注意事項：

- `**/tests/` 受 `.gitignore` 排除（列為「maintenance sovereign 產物、非 source-of-record」），
  因此本階段測試不會進入版控；若日後由維護流程重生測試檔，需保留本節所列斷言。
- checkpoint 目前只存權重與設定，**未含 optimizer 狀態**，續訓（resume）待 Phase 2 補齊。
- D1 修復後帶 mask 的路徑會材料化 (B,1,S,S) 遮罩；無 mask 路徑維持 SDPA 內建 causal（較快）。

## 5. 建置藍圖

前置原則：**先修 D1–D5、再談訓練、最後才接線**；每一期都要通過 `python -m governance_rule.execution.audit`。

### Phase 0 — 原生核心正確性與存讀（先行）

- 修 D1（合成 causal＋padding 遮罩）、D2（decode 傳入 `prefix_len + i` 的 position_ids）、D3、D5。
- 新增 `native_transformer/checkpoint.py`：`save_checkpoint`／`load_checkpoint`，內容含 config、模型 state_dict、
  tokenizer state 與 sha256；落地目錄建議 `Standalone tools/local-model/xingcheng/runtime/models/`。
- 測試：因果性、RoPE 位置、cache 等價、存讀往返、10 句 overfit 收斂 smoke。
- 驗收：以上測試全綠；不新增服務路徑（維持未接線）。

### Phase 1 — Base Model 接線（可逆、可回退）

- tokenizer 決策：先維持位元組級但把 vocab 對齊（保留 256+ 合併空間），BPE 留待 Phase 2。
- 在模型引擎層新增原生 engine 與 **feature flag**（預設關閉、fail-closed），輸出必須誠實標記
  `star_native_model_used: True`／`third_party_weights_used: False`，並維持「模型核心與網路功能分離」。
- 新增元件須登錄 `architecture_registry.json`；法典鏡像屬唯讀區，需治理權威核准後更新。
- 驗收：離線 CLI 可載入 Phase 0 的 checkpoint 生成；服務開關切換有審計事件；關閉時行為與現況完全一致。

### Phase 2 — Pretraining

- 語料管線：僅從已授權來源（本機既有語料、RAG 文件、法典文本）產生 JSONL（含來源 hash 與授權標記）；
  對外網路一律走受治理工具路徑。
- （可選）訓練 BPE tokenizer 並凍結 vocab。
- 預訓練 run：先做**可行規模**（例如 10M–50M 參數、CPU／單卡、億級以下 token），
  產出 loss/perplexity 曲線與樣本抽檢；硬體預算是硬約束（現況 torch 為 CPU 版）。
- 訓練必須走 `transformer_training_repository` 的 job 狀態機（需新增 executor），
  `automatic_weight_replacement = 0` 不變式不得破壞。
- 驗收：可重現的 checkpoint＋訓練報告；perplexity 相對隨機初始化有明確下降。

### Phase 2 執行結果（v0，2026-09-19）

- 語料：`training/corpus.py` 從第一方來源（法典、docs、local-model、src-core、shared-layer）建置，
  866 篇／14.50M 字元，train/val 分離並輸出 `manifest.json`（含每檔 sha256）；
  產物：`xingcheng/runtime/corpus/`（train.jsonl sha256 `205734ba…`、val.jsonl sha256 `c752b26a…`）。
- 自有 tokenizer：`bpe.py` 以成熟 `tokenizers` 函式庫訓練 byte-level BPE，
  詞表 8,192、特殊符號 0–3（pad/bos/eos/unk），artefact 凍結於
  `xingcheng/runtime/tokenizers/xingcheng-bpe-8k/`（sha256 `7ee7523b…`），`state_dict()` 內嵌完整詞表。
- 預訓練：`training/pretrain.py`（packed blocks、AdamW、warmup＋cosine、梯度累積與裁剪、
  optimizer 狀態續訓、驗證困惑度）。首個自有權重 v0（`XingChengConfig.small`，5,048,576 參數）：
  4.10M tokens、596.8s（CPU ~6,863 tokens/s）、train loss 9.06 → 3.76、**val perplexity 104.88**；
  checkpoint：`xingcheng/runtime/models/xingcheng-native-v0/final.pt`（`star-transformer-checkpoint/v1`）。
- 已驗證：以 `Generator` 直接載入自有權重生成（greedy／sampling），不經 Ollama。
- v0 限制：CPU-only（torch 2.13.0+cpu）；語料以法典／程式碼為主，中文散文比例不足；
  未做 SFT（尚為續寫模型）；**尚未接入服務路由**（Phase 1 待辦：星澄獨立推理、Ollama 僅教師）。

### Phase 3 — Post-training

- 實作 `star-transformer-sft/v1` 序列化器：`language_training_example` → JSONL（train／validation 分割＋sha256）。
- SFT（先 LoRA／adapter）→ 產生 `adapter_candidate` → 評估（perplexity ＋ 現有 `capability_evaluation` 13 項 A/B）
  → 才允許 `adapter_release`；release 表不可變、可回滾。
- 偏好訓練：先把 owner teaching 與既有 approve／reject 流程升級成 chosen／rejected 收集，再導入 DPO。
- 工具呼叫：定義 tool-call schema 與訓練樣本格式（目前完全空白）。
- 驗收：adapter 在保留集勝過 base；未達門檻不得發布；全程審計可追溯。

- 蒸餾語料：`training/distill.py`——grounded topics＋Ollama 教師

### Phase 4 — Inference System（原生路徑）

- KV／prefix cache 管理（先原生路徑；Ollama 路徑維持現狀並保留其治理標記）。
- 上下文壓縮（原生：分段摘要或滑動視窗；Ollama：維持現有窗格階梯）。
- 取樣 API 擴充：per-request `top_p`／`seed`／`repetition_penalty`（原生 sampler 已有，需接線）。
- 加速：INT8 先接、INT4 需補 4-bit packing；Triton RoPE 目前只是回退 stub（`kernels/rope.py:100-102`）。
- 驗收：量化前後困惑度差異在門檻內；延遲／吞吐基準可重現；推論結果標記與現行治理相容。

### Phase 4 完成結論（2026-09-19）

- 取樣 API：per-request `top_p`／`seed`／`repetition_penalty`／`top_k`／
  `temperature` 全鏈接線；seed 在引擎鎖內固定 → 同 seed 輸出逐字確定性。
- 上下文：`sliding_window=True` 保留 prompt 尾端截斷（`prompt_truncated`
  標記），預設仍 fail-closed。
- 量化：`quantize=8`／`quantize=4` engine 選項＋`XINGCHENG_NATIVE_QUANTIZATION`；
  **INT4 已補真 4-bit packing**（`pack_int4`/`unpack_int4`，兩值/byte，
  權重記憶體 = FP32 的 1/8）。
- Triton RoPE：`_rope_triton` 已是真正的 elementwise Triton kernel
  （fused cos/sin gather 成 (B,S,D)）；無 Triton/CUDA 環境仍退回 PyTorch
  參考實作（本機無 triton，GPU 路徑待有環境時驗證）。
- 基準：`benchmark.py` 產出 `star-native-benchmark/v1`（延遲序列、tok/s、
  checkpoint sha256、FP32-vs-INT8 困惑度比較）。
- 已實測：v1-gpu checkpoint（32.7M tokens、val ppl 20.04）經原生引擎

## 6. 不變式（建置期間不得破壞）

1. 模型核心與網路功能分離；所有對外存取走受治理工具路徑。
2. 第三方權重與原生權重的來源標記必須誠實（`third_party_weights_used` 等旗標不得錯標）。
3. `automatic_weight_replacement = 0`：任何權重替換都必須經明確流程與審計，不得自動生效。
4. 法典（`governance_rule/codex/*`）為唯讀；新增元件與架構變更需經治理權威。
5. 訓練資料只收已授權、已審核來源；外部模型輸出不得直接進入自我訓練（現行 `infer_transformer.py:95` 行為保留）。
6. 主線裁決（2026-09-19）：完整模型以 Python + PyTorch 實作（訓練與推論皆然）；C++ 系下沉（`native/` pybind11 / Gluon / CUDA C++ / PTX）留給後續自研推論引擎承接，不屬於本模型核心範圍。

## 7. 風險與未決事項

- **硬體**：CPU-only torch 下，Phase 2 只能做可行性驗證，不能產出可用基礎模型；需先決定算力預算。
- **語料合法性**：可取得的中文語料授權與品質需治理裁決。
- **定位重疊**：原生模型與 Ollama 的關係（替代／互補／僅離線備援）需先定案，否則 Phase 1 接線會反覆。
- **評估不足**：目前沒有語言模型層級評估（perplexity、保留集、生成品質），Phase 2 前必須補。
- **文件同步**：新增模型元件後，`architecture-tool-local-model.md` 與 registry 需同步（唯讀區需核准）。
